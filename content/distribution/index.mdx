## The lifecycle of a change

```text
issue → RFC (if cross-cutting) → branch → implement → test
      → pull request → review → merge → release (ISO tag or repo push)
```

Every distribution change starts from a real problem in an issue tracker.
Cross-cutting changes (new edition, default-package changes, installer
behavior) start in the [rfcs repo](https://github.com/parchlinux/rfcs)
first; the [contribution workflow](/start/contribution-workflow/) explains
the doors.

## Where the risk lives

<Callout kind="warning" title="Distribution changes reach everyone">
  A broken theme update bricks logins for thousands of users; a bad
  Calamares change corrupts installs. Distribution code reviews are stricter
  than app reviews, and testing expectations are higher: boot both
  firmwares, test the installer in a VM, and test upgrades from a real
  installed system before asking for review.
</Callout>
