## The three canonical test plans

Everything else is a variation of three plans. Copy them into your PR
description and tick the boxes:

<Steps>
  <Step title="Application plan">
    Build from clean checkout, unit tests pass, launch on Wayland, exercise
    the primary flow, keyboard-only pass, dark theme, Persian locale, then
    package it and repeat after `pacman -U`.
  </Step>
  <Step title="Package plan">
    Clean chroot build, `namcap` clean, install/upgrade/remove cycle, file
    list review, dependency check (`ldd` for binaries), desktop file
    validation. Detail in [testing packages](/testing/testing-packages/).
  </Step>
  <Step title="ISO plan">
    Build from the profile, boot in QEMU (BIOS and UEFI), installer run with
    auto and manual partitioning, post-install boot and update, then one
    real-hardware pass before release. Detail in
    [testing ISOs](/testing/testing-isos/).
  </Step>
</Steps>

## Principles

<Checklist>
  - **Test on a system that looks like a user's:** current packages, one
    desktop, real fonts. A pristine build machine hides integration bugs.
  - **Write down what you tested.** Untested claims do not count; the PR
    description is the test report.
  - **Automate the boring parts** (builds, linting, boot smoke tests) and
    spend human attention on the parts that need judgment (UX, RTL,
    installer edge cases).
  - **Regressions get tests.** Every bug that ships once should be caught
    automatically the second time.
</Checklist>
